# CSI Data Contracts

This document defines the data contracts exchanged across the CSI-based activity and fall detection pipeline.

The system follows four main data stages:

```text
ESP32
  │
  │ CSI Packet
  ▼
Gateway
  │
  │ Window
  ▼
Preprocessing / Models
  │
  │ Model Output
  ▼
Gateway / Backend
  │
  │ Event
  ▼
Dashboard / Alert System
```

---

## 1. CSI Packet

### ESP32 → Gateway

The CSI Packet contains raw Wi-Fi Channel State Information (CSI) and metadata collected by the ESP32 receiver.

### Example

```json
{
  "schema_version": 1,
  "node_id": "rx1",
  "seq": 10234,
  "ts_us": 123456789,
  "rssi": -48,
  "noise_floor": -92,
  "channel": 6,
  "bw": 20,
  "len": 128,
  "csi": [0, 0, 12, -5]
}
```

### Fields

| Field            | Type    | Description                               |
| ---------------- | ------- | ----------------------------------------- |
| `schema_version` | integer | Version of the packet schema              |
| `node_id`        | string  | Unique ID of the ESP32 receiver           |
| `seq`            | integer | Sequential packet number                  |
| `ts_us`          | integer | Timestamp in microseconds                 |
| `rssi`           | integer | Received Signal Strength Indicator in dBm |
| `noise_floor`    | integer | Estimated noise floor in dBm              |
| `channel`        | integer | Wi-Fi channel used for CSI acquisition    |
| `bw`             | integer | Channel bandwidth in MHz                  |
| `len`            | integer | Length of the CSI payload                 |
| `csi`            | array   | Raw CSI values                            |

### Purpose

The CSI packet is the lowest-level data unit in the system.

It is used to:

* Collect CSI measurements.
* Track packet sequence numbers.
* Monitor packet loss.
* Monitor RSSI and noise floor.
* Preserve timing information.
* Provide raw CSI data for preprocessing.

# 2. Window

### Preprocessing → Models

A Window represents a fixed-size segment of processed CSI data prepared for machine learning inference.

### Example

```json
{
  "schema_version": 1,
  "window_id": 4021,
  "node_id": "rx1",
  "ts_start_us": 123400000,
  "ts_end_us": 128400000,
  "fs_hz": 100,
  "shape": [52, 500],
  "dtype": "float32",
  "preprocess_version": "v1",
  "data_path": "windows/4021.npy"
}
```

### Fields

| Field                | Type    | Description                                |
| -------------------- | ------- | ------------------------------------------ |
| `schema_version`     | integer | Version of the window schema               |
| `window_id`          | integer | Unique identifier for the processed window |
| `node_id`            | string  | Source ESP32 receiver ID                   |
| `ts_start_us`        | integer | Window start timestamp                     |
| `ts_end_us`          | integer | Window end timestamp                       |
| `fs_hz`              | integer | Sampling frequency in Hz                   |
| `shape`              | array   | Shape of the processed data                |
| `dtype`              | string  | Data type of the stored values             |
| `preprocess_version` | string  | Version of preprocessing pipeline          |
| `data_path`          | string  | Path to the `.npy` data file               |

### Data Shape

```text
[52, 500]
```

This indicates that the processed window contains:

* `52` CSI-related features/subcarriers/channels
* `500` time samples

The exact interpretation of the first dimension depends on the CSI preprocessing configuration.

### Purpose

The Window provides a standardized input format for machine learning models.

The preprocessing stage can include operations such as:

```text
Raw CSI
   ↓
Cleaning
   ↓
Filtering
   ↓
Normalization
   ↓
Windowing
   ↓
Feature Tensor
   ↓
Model
```

# 3. Model Output

### Models → Gateway / Backend

The Model Output contains the prediction generated by the machine learning model for a specific CSI window.

### Example

```json
{
  "schema_version": 1,
  "window_id": 4021,
  "ts_us": 128400000,
  "model_version": "cnn-0.1",
  "activity": "walk",
  "activity_probs": {
    "empty": 0.02,
    "walk": 0.92,
    "stand": 0.02,
    "sit": 0.02,
    "lie": 0.02
  },
  "fall_prob": 0.04,
  "confidence": 0.92,
  "calibrated": false
}
```

### Fields

| Field            | Type    | Description                                              |
| ---------------- | ------- | -------------------------------------------------------- |
| `schema_version` | integer | Version of the model-output schema                       |
| `window_id`      | integer | ID of the input CSI window                               |
| `ts_us`          | integer | Prediction timestamp                                     |
| `model_version`  | string  | Version of the ML model                                  |
| `activity`       | string  | Predicted activity                                       |
| `activity_probs` | object  | Probability for each supported activity                  |
| `fall_prob`      | float   | Estimated probability of a fall                          |
| `confidence`     | float   | Confidence associated with the prediction                |
| `calibrated`     | boolean | Indicates whether the probabilities have been calibrated |

### Supported Activities

The current example supports:

```text
empty
walk
stand
sit
lie
```

### Example Interpretation

The model output:

```json
"activity": "walk",
"confidence": 0.92
```

means that the model predicts the person is walking with a confidence value of `0.92`.

The fall probability is:

```json
"fall_prob": 0.04
```

which represents the model's estimated fall probability for this window.

# 4. Event

### Gateway → Backend / Dashboard

An Event represents a higher-level system decision generated from model outputs and system rules.

Unlike the Model Output, which represents an ML prediction, an Event represents something that should be communicated to the backend or dashboard.

### Example

```json
{
  "schema_version": 1,
  "event_id": "b3f1c2e0-0000-0000-0000-000000000000",
  "ts": "2026-09-19T10:15:00Z",
  "gateway_id": "gw1",
  "zone": "living_room",
  "type": "possible_fall",
  "status": "Possible Fall Detected",
  "confidence": 0.94,
  "level": "critical",
  "post_event_state": "limited_movement",
  "action": "alert"
}
```

### Fields

| Field              | Type               | Description                            |
| ------------------ | ------------------ | -------------------------------------- |
| `schema_version`   | integer            | Version of the event schema            |
| `event_id`         | UUID/string        | Unique event identifier                |
| `ts`               | ISO 8601 timestamp | Event timestamp                        |
| `gateway_id`       | string             | Gateway that generated the event       |
| `zone`             | string             | Physical zone where the event occurred |
| `type`             | string             | Event type                             |
| `status`           | string             | Human-readable event status            |
| `confidence`       | float              | Confidence associated with the event   |
| `level`            | string             | Event severity level                   |
| `post_event_state` | string             | Detected state after the event         |
| `action`           | string             | Action triggered by the event          |

### Example Event Types

```text
possible_fall
activity_change
inactivity
presence_detected
presence_lost
```

The supported event types should be defined by the system requirements.

# 6. Relationship Between Messages

Each stage is connected through identifiers and timestamps.

```text
CSI Packet
    │
    │ node_id + timestamp
    ▼
Window
    │
    │ window_id
    ▼
Model Output
    │
    │ prediction + confidence
    ▼
Event
```

For example:

```text
node_id = rx1
       │
       ▼
window_id = 4021
       │
       ▼
model_version = cnn-0.1
       │
       ▼
activity = walk
       │
       ▼
fall_prob = 0.04
       │
       ▼
Event Engine
       │
       ▼
possible_fall / alert
```

# 7. Versioning

All contracts contain:

```json
"schema_version": 1
```

This allows the format to evolve without breaking older components.

For example:

```text
schema_version: 1
```

can later become:

```text
schema_version: 2
```

when fields or structures change.

The model output also contains:

```json
"model_version": "cnn-0.1"
```

while preprocessing uses:

```json
"preprocess_version": "v1"
```

This makes it possible to identify exactly which preprocessing pipeline and model produced a prediction.

# 8. Data Traceability

The system should maintain traceability from the raw CSI data to the final event.

```text
ESP32 Packet
     │
     ├── node_id
     ├── seq
     └── ts_us
          │
          ▼
      Window
          │
          ├── window_id
          ├── node_id
          ├── ts_start_us
          └── ts_end_us
                │
                ▼
          Model Output
                │
                ├── window_id
                ├── model_version
                ├── activity
                └── fall_prob
                      │
                      ▼
                    Event
                      │
                      ├── event_id
                      ├── gateway_id
                      ├── zone
                      └── action
```

This traceability is important for:

* Debugging.
* Model evaluation.
* Reproducing predictions.
* Investigating false positives and false negatives.
* Monitoring system performance.
* Auditing generated events.

---

# 9. Summary

The system uses four primary data contracts:

| Stage | Message      | Direction                   | Main Purpose                 |
| ----- | ------------ | --------------------------- | ---------------------------- |
| 1     | CSI Packet   | ESP32 → Gateway             | Raw CSI acquisition          |
| 2     | Window       | Preprocessing → Models      | ML-ready CSI data            |
| 3     | Model Output | Models → Gateway/Backend    | Activity and fall prediction |
| 4     | Event        | Gateway → Backend/Dashboard | System-level event and alert |

The contracts provide a structured interface between hardware acquisition, preprocessing, machine learning, event processing, and the backend/dashboard.
